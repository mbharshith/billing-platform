1. Overview

Type
Multi-tenant POS + storefront

Chain-wide topology (markets → brands → stores → outlets); operational data is outlet-scoped.

Persistence
Dexie / IndexedDB v9

Local-first. Schema v9 stamps outletId + [storeId+outletId] compound index on every tenant table.

Frontend

pnpm monorepo. No module federation - three apps compose via Vite aliases into packages/@billing/*.

Topology

markets, brands, outlets, stores, users, auditLog - chain-wide.

Outlet-scoped

38 tenant tables key on [storeId+outletId]. Each branch owns its own book.

Config

Menu, kitchen, recipes, warehouses, coupons - fanned per outlet on seed & migration.

Transactional

Sales, POs, GRNs, expenses, lending - backfilled to primary; new rows stamped by cashier context.

2. Data model (Dexie v9)

Every tenant table carries a compound key [storeId+outletId]. Outlet tables are cloned once per outlet on seed / migration; foreign-key columns (*Id) are rewritten with the same ::outletId suffix so references resolve inside a single outlet.

4. Backend design

Today Outletly is local-first (Dexie / IndexedDB). The backend below is the target when we lift it to a shared server — it inherits the outlet-scoping model verbatim so the frontend contract barely changes.

Recommended stack

API
FastAPI + Python 3.12

Async, OpenAPI free, Pydantic v2 for schema-in / schema-out. Auto-generates the TS client the frontend consumes.

Database
Postgres 16

Row-level security on every tenant table (store_id + outlet_id). Logical replication for read replicas.

Cache / Queue
Redis 7

Session tokens, rate limits, KDS pub/sub, Celery broker + result backend.

Object storage
S3 / R2

Product images, GRN attachments, generated invoice PDFs, WhatsApp media.

Background
Celery + Beat

EOD roll-ups, WA campaign fan-out, GRN reconciliation, sync merge jobs.

Realtime
WebSockets (Starlette)

KDS ticket stream, live-orders kanban push, table-status sync per outlet.

Auth
JWT (RS256) + PIN

Access (15 m) + refresh (30 d) tokens. Cashiers login by 4-digit PIN scoped to their outlet.

Observability
OTel + Grafana Loki

Distributed traces per request, structured logs tagged with store_id/outlet_id.

Authentication & multi-tenant scoping

Token model

  • Access token (JWT, RS256, 15 min): subject user_id, claims role, store_id, allowed_outlets[].
  • Refresh token (opaque, 30 d): stored server-side in Redis, revokable per device.
  • PIN mode for cashiers: POST /auth/pin with 4-digit PIN + outlet_id issues a scoped, short-lived (8 h) shift token.
  • Vendor role gets a wildcard allowed_outlets: ["*"] for HQ reporting; every other role is bounded.

Request scoping

  • Every mutating request MUST include X-Store-Id + X-Outlet-Id headers.
  • Middleware verifies both are in the token's allowed_outlets — else 403.
  • Middleware sets Postgres SET app.store_id = ...; SET app.outlet_id = ...; for the connection lifetime.
  • Every tenant table has RLS: USING (store_id = current_setting('app.store_id') AND outlet_id = current_setting('app.outlet_id')).
  • Result: even a SQL-injection escaping the ORM cannot read another outlet's row.

Offline sync protocol

The frontend stays Dexie-first. The backend adds a delta protocol so a laptop that lost wifi mid-service catches up cleanly when it reconnects.

1. Push queue

Client stamps every mutation with a client-generated ULID + client_seq. Queue is a Dexie table sync_outbox. POST /sync/push flushes it; server returns per-op {ok, canonical_id}.

2. Delta pull

GET /sync/pull?since=<server_cursor> returns every row modified after cursor, grouped by table. Client upserts and advances the cursor.

3. Conflict rule

Last-write-wins by updated_at for config tables. Sales & payments are append-only (voids are new rows) so they cannot conflict — deterministic merge.

Postgres schema notes

  • Every tenant table has (store_id, outlet_id, id) as the natural key; id is a ULID (sortable, collision-safe across offline clients).
  • sales is partitioned monthly by completed_at. Old partitions detach to cold storage after 24 months.
  • audit_log is append-only with a BRIN index on at and a partial index on action for hot filters.
  • Every updated_at column is maintained by a shared trigger; used by /sync/pull as the delta cursor.
  • Foreign keys use ON DELETE RESTRICT except audit_log which is ON DELETE SET NULL for the target_store_id (stores can be archived without shredding history).
  • All *_id columns are indexed. Compound index (store_id, outlet_id, active) covers 90% of admin list queries.

Scalability: what happens at 10x, 100x, 1000x

Numbers below assume a POS-shaped workload: bursty during meal hours, quiet in between; write:read roughly 1:20; reports are the read hot-spot.

Tier Outlets Orders/day Peak orders/sec Infra Est. cost/mo (USD)
Pilot 1–10 ~1k 2–5 1× API pod, 1× managed PG (db.t3.small), 1× Redis (cache.t3.micro), 1× Celery worker $60–120
Growth 100 ~50k 10–25 3× API pods, PG r6g.large + 1 read replica, Redis m6g.large, 2 Celery workers $450–700
Scale 1,000 ~500k 100–250 10–20 API pods (autoscale), PG r6g.2xlarge + 3 read replicas, Redis m6g.xlarge cluster (3 shards), 6 Celery workers, 2 regions $3.5k–6k
Chain 10,000 ~5M 1k–2.5k 50–100 API pods, PG sharded by store_id hash (4–8 primaries) + read replicas per shard, Redis cluster (12+ shards), 20+ Celery workers, 3–4 regions, ClickHouse for reports $25k–60k

Where the bottlenecks bite (and how we push them out)

1st bottleneck (Growth → Scale)
Report queries on the sales table

Big date-range aggregations lock rows and starve write throughput. Push it out with: (a) route all /reports/* to a read replica, (b) materialised views refreshed every 5 min for chain-wide roll-ups, (c) column-store extension (citus) or ClickHouse mirror once Chain tier hits.

2nd bottleneck (Scale → Chain)
Write throughput on sales

Single Postgres primary caps around ~5–10k sustained writes/sec. Push out with: (a) monthly partitions already declared, (b) shard by hash(store_id) so each shard owns a slice of stores — RLS still works, only the query planner sees the shard router. Vendor / chain-wide reports fan out through Citus.

3rd bottleneck
WebSocket fan-out for KDS

Each pod holds ~10k concurrent WS connections comfortably. At 100k+ outlets simultaneously connected, add a WS-only tier fronted by NLB; Redis pub/sub sharded per-outlet keeps fan-out local.

4th bottleneck
Redis on Celery broker load

If EOD roll-ups all fire at 23:59 UTC we burst-load Redis. Push out with: (a) Redis Cluster with 3+ shards, (b) stagger schedules across market timezones (they naturally spread across 24h), (c) migrate high-fan-out queues (WA campaigns) to SQS or a Kafka broker if per-message ordering demands it.

Horizontal scaling story (in one paragraph)

FastAPI pods are stateless — every dependency (session, cache, queue, DB) is external, so autoscale is replicas = ceil(rps / 500). Postgres scales vertically first (bigger instance) then horizontally via Citus sharding on hash(store_id); because RLS filters on (store_id, outlet_id) and every query includes those, the shard key is always in the WHERE clause. Redis scales via Cluster mode with hash slots. WebSockets scale by adding pods behind an NLB; Redis pub/sub bridges message delivery across pods so a KDS bump from POS pod #7 reaches KDS screen on pod #23. Object storage (S3/R2) is horizontally scalable by definition. The only thing that ever needs a data migration is Postgres sharding — and that's a background job because store_id was in every row from day one.

Why not the other popular stacks?

Alternative What it does well Why it loses for our workload
Node.js + Express / NestJS Same TS on both ends; huge ecosystem; excellent WS story. Runtime schema validation needs Zod / class-validator bolted on. OpenAPI is a plugin, not a first-class citizen — contract drift shows up in prod. Reporting workloads (heavy joins, pandas-style transforms) push you back to a Python worker anyway; two languages, two ops stories.
Go + Gin / Fiber / Echo Fastest and cheapest per RPS; single static binary; no GIL. 3–5× the code for our CRUD-dominant surface (122 endpoints). No auto-OpenAPI. Reporting / ETL story is DIY. Local hire pool (Bengaluru, our home market) skews heavily Python/JS. Go is a great second service — e.g. the KDS ticket router — not the whole platform.
Ruby on Rails Legendary developer velocity for CRUD; ActiveRecord is a joy. Sync request model + GIL + 1–2× the memory footprint per request; running WS + async jobs means AnyCable + Sidekiq add-ons. Overall throughput per dollar sits well below FastAPI on the same box.
Django REST Framework Batteries-included admin, ORM, auth, migrations. Sync-first; WebSockets need Channels + Daphne (extra process); DRF serializers duplicate what Pydantic already gives us for free. We'd pay the batteries tax without using half of them.
Java / Spring Boot Enterprise-grade; famously scalable; strongly typed. JVM cold-start + memory footprint on autoscale pods hurts. 3–5× the LOC for equivalent surface. Team ramp-up steep. Correct fit for a huge enterprise; overkill for us.
Serverless (Lambda + API Gateway) Zero idle cost; auto-scale to zero. Cold-start latency (200–800 ms) is unacceptable at the POS counter. WebSockets on API Gateway are quirky and expensive. Long-running Celery-like jobs need Step Functions gymnastics. Costs cross over above ~1 rps sustained.
MongoDB Flexible schema; sharding built in; great local dev story. No true row-level security. Multi-document ACID landed only in 4.2 and comes with a perf tax. Reports (SUM/GROUP BY across joined collections) are painful — the aggregation pipeline is Turing-complete but writing a 5-way join in it is not fun. Money should not be eventually-consistent.
DynamoDB Fully managed; single-digit-ms reads; scales infinitely on a good partition key. 400 KB item limit trips on sales with many line items + modifiers. No ad-hoc reporting queries (need Athena / OpenSearch mirror). Cross-region strong consistency isn't native. Cost gets ugly on read-heavy report loads.
MySQL / MariaDB Universally understood; every hire knows it; every hoster runs it. No true RLS — you fake it with views + @current_tenant variables; one careless raw query and the tenant boundary vanishes. JSONB is second-class. Partial and expression indexes are weaker. It'd work — but every dollar we save on hiring we'd pay back in security audits.
Kafka (as event bus) Ordered, durable, replayable event log; industry standard. Operational complexity: ZooKeeper (or KRaft), broker sizing, partition planning, exactly-once semantics. Overkill until we're firing millions of events/day. Redis pub/sub covers us up to Scale tier; we'd swap in Kafka only when the analytics pipeline demands replay.
GraphQL (Apollo / Hasura) Client picks exactly the fields it needs; strongly-typed schema. Cache invalidation and query cost analysis are non-trivial. N+1 query risk on multi-outlet reports. Our clients are first-party — the flexibility we'd pay for isn't a payoff we'd cash in.

Deployment

Runtime

  • Docker image, single Dockerfile (multi-stage: builder + runtime).
  • Deploy target: Fly.io regions per market (bom/sin/ord) OR AWS EKS.
  • Autoscale on rps + p95_latency. Zero-downtime deploys via rolling.
  • Migrations run via a one-shot job before the rolling update (Alembic).

Non-functional targets

  • Availability: 99.9% (43 min/month allowed). Multi-AZ Postgres.
  • Latency: p95 < 200 ms for reads, < 400 ms for writes (in-region).
  • Rate limit: 60 rps / outlet (soft), 5 rps / IP for auth endpoints (hard).
  • Backups: Postgres continuous WAL to S3 + nightly logical dump. RPO 5 min, RTO 30 min.
  • Secrets: AWS SSM / Vault. Never in env files. Rotated quarterly.

6. Security

A single-tenant SaaS gets away with lazy security. A multi-tenant POS handling real money across thousands of outlets does not. Security here is enforced at three layers — edge, app, and database — so no single failure breaches the tenant boundary.

Defense in depth

Edge
Cloudflare WAF · DDoS shield · TLS 1.3 · bot rules · geo blocks
Blocks the top-100 automated attacks before they touch the origin
App middleware
JWT verify → RBAC → tenant scope → rate limit → input validate
Every request runs the same pipeline in the same order — no per-route bypass paths
Database
Row-Level Security policies · least-privilege DB roles · encryption at rest
Even a bug that bypasses app-layer scoping cannot read another outlet's data

Authentication

Password login (owners / admins)

  • Passwords hashed with Argon2id (m=64 MB, t=3, p=4). Never bcrypt.
  • Min 12 chars, checked against HIBP pwned list on set.
  • Rate limit: 5 attempts / 15 min / IP + username. Lockout at 10 with email alert.
  • Optional TOTP MFA (RFC 6238) — enforced for role owner, opt-in below.
  • WebAuthn / passkeys planned for admin console.

PIN login (cashiers)

  • 4-digit PIN — but PIN alone is not the credential.
  • Real credential = (PIN, outlet_id, device_id). PIN validates only against the outlet's roster.
  • Rate limit: 3 wrong attempts → 60 s lockout, exponential thereafter.
  • Issued token is shift-scoped: expires at end of shift OR 8 h, whichever first.
  • Device pairing required: unknown device_id triggers admin approval flow.

Token model

  • Access token: JWT, RS256, 15-min TTL. Claims: sub, role, store_id, allowed_outlets[], device_id, jti.
  • Refresh token: opaque 256-bit random, 30-d TTL, stored in Redis (SETEX). Rotation on use (one-time-use); reuse detection revokes the whole family.
  • Signing key rotated quarterly via /.well-known/jwks.json; old key stays verifiable for 24 h grace.
  • Storage on client: access in memory only; refresh in httpOnly + Secure + SameSite=strict cookie. Never localStorage → XSS-proof.

Session & account safety

  • Every session shows in My Devices; user can revoke individually or nuke all.
  • Login from a new device / country → email + WA alert with revoke link.
  • Password change → revoke every refresh token (except current device).
  • Suspicious activity (3+ 403s in 60 s) → auto-revoke session + audit event.

Data protection

Encryption

  • In transit: TLS 1.3 only, HSTS preload, OCSP stapling. Internal service-to-service uses mTLS.
  • At rest: AES-256 via KMS. Postgres, Redis persistence, S3 buckets all SSE-KMS-encrypted with per-market keys.
  • Field-level: customer PII (mobile, email, address) encrypted with envelope encryption; app decrypts on read. Backup dumps stay ciphered.
  • Keys: AWS KMS / GCP KMS, never in code. Rotated automatically every 90 days.

PII & data minimisation

  • Only mobile + first name required for a customer record; email, DOB, address optional.
  • Card details never touch our servers — Razorpay / Stripe tokenisation only (PCI-DSS SAQ-A scope).
  • PII fields masked in logs by structured logger ({ mobile: "98****3210" }).
  • Right-to-erasure endpoint: soft-anonymise (replace with [REDACTED]) while keeping sale rows intact for accounting.
  • Data-retention policy: raw access logs 90 d, audit log 7 y (statutory), voided sales anonymised after 24 mo.

Payments

  • Never store PAN / CVV / expiry — the app never sees them. Card entry runs in Razorpay/Stripe's iframe.
  • PCI-DSS SAQ-A scope (merchant hosting-only). Yearly self-assessment.
  • Refund flow requires manager PIN + reason logged.
  • Cash drawer opens are audited (who, when, why); mismatches at EOD reconciliation flagged.

Backups & disaster recovery

  • Postgres continuous WAL to S3 + nightly pg_dump to a cross-region bucket.
  • RPO 5 min, RTO 30 min. Restore drill runs monthly against a staging cluster.
  • Backup buckets are versioned + Object-Lock (WORM) 35 d — ransomware cannot delete history.
  • Encryption keys stored in a separate KMS account — a compromise of the DB account cannot decrypt.

Frontend hardening

  • CSP strict-dynamic: no inline scripts; nonces on every deploy. Blocks XSS reflected or stored.
  • Trusted Types where supported — prevents raw string sinks to innerHTML.
  • CSRF: refresh cookie is SameSite=strict; state-changing endpoints require the access-token header (double-submit).
  • XSS: React auto-escapes; ESLint rule bans dangerouslySetInnerHTML except behind a review comment.
  • Clickjacking: X-Frame-Options: DENY and CSP frame-ancestors 'none'.
  • Subresource integrity on every CDN script (Tailwind, Chart.js).
  • Secrets never in client bundles — only publishable keys (Razorpay rzp_live_pub_*) ever ship.
  • Local-first browser storage: IndexedDB rows encrypted with the user's session key (WebCrypto AES-GCM) so a stolen laptop with the browser closed reveals nothing.

Secrets, supply chain, incident response

Secrets management

  • AWS SSM Parameter Store / HashiCorp Vault. Never .env in git.
  • Pre-commit hook: gitleaks blocks pushes containing secrets.
  • Ephemeral IAM creds for CI (OIDC federation), no long-lived AWS keys.
  • Rotation: DB creds 90 d, JWT signing key quarterly, webhook secrets on demand.

Supply chain

  • Lockfiles committed (uv.lock, pnpm-lock.yaml). No ^ ranges resolved fresh in prod builds.
  • Dependabot + pip-audit + npm audit + trivy on the container image; CI fails on High/Critical CVEs.
  • SBOM (CycloneDX) generated per release, published to internal registry.
  • Container images signed with cosign; admission controller rejects unsigned images in prod.

Incident response

  • Runbook per severity (SEV-1…3) with response times.
  • Kill switches: revoke-all-tokens, disable-signup, mark-outlet-quarantine.
  • Post-mortems blameless, published to /docs/incidents/. Action items tracked to close.
  • Bug bounty scope + disclosure policy at /.well-known/security.txt.

Compliance posture

  • PCI-DSS SAQ-A — merchant hosting-only (card entry in gateway iframe).
  • India DPDP Act 2023 — data minimisation, purpose limitation, right-to-erasure, DPO contact in footer.
  • GDPR — DPA available for EU customers, in-region hosting for EU tenants, 72-h breach notification workflow.
  • SOC 2 Type II — roadmap; controls (access review, change mgmt, MFA, backup) already implemented and evidence-captured.
  • GST invoicing — conforms to CBIC format; digitally signed invoices where the outlet opts in.

What's already true today (local-first build)

Outletly is Dexie / IndexedDB right now — there is no server to attack. The relevant surface today is:

  • Outlet scoping enforced by the useTable hook: [storeId+outletId] compound index in every query. Prior audit sealed three cross-outlet leaks (reports, dashboard, SalesContext fallback).
  • PIN / password lives client-side in seed users only; do not deploy the demo build as-is publicly.
  • All CDN scripts loaded with modern browsers' built-in integrity checking; no third-party trackers.
  • The plan above is the target when we lift to a server — every item is deliberately called out so the migration doesn't grow security debt.

7. Data flow

Read (any admin page)

  1. User logs in → AuthContext sets currentUser.
  2. readOutletFor(user) defaults currentOutletId to user.storeId (primary).
  3. User can switch via <OutletPicker /> - updates currentOutletId, persists in localStorage['active-outlet:<userId>'].
  4. Any admin page calls useTable<X>('tableName').
  5. Hook inspects Dexie schema, finds [storeId+outletId], runs db.X.where('[storeId+outletId]').equals([sid, oid]).
  6. Dexie's live query pushes updates whenever the underlying rows change.

Write (cashier records a sale)

  1. Cashier picks items, taps Charge → CashierCheckout modal opens.
  2. Selects order type / table / customer as needed.
  3. On confirm: SalesContext.recordSale(input) is called.
  4. Input is stamped: storeId = currentStoreId, outletId = currentOutletId, cashierId = currentUser.id.
  5. Invoice number is minted per outlet (outletSettings sequence).
  6. Dexie put in db.sales; live queries in Reports / Dashboard / LiveOrders update immediately.
