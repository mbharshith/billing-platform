When each option starts to hurt

A) Supabase
  • DB > 500 MB → upgrade to Pro ($25/mo)
  • Realtime connections > 200 concurrent
  • Bespoke business logic — edge functions are limited
  • Multi-region — single region on free
B) Neon + Fly
  • Fly free VMs sleep — cold-start 5–10 s on first hit
  • Neon 0.5 GB → upgrade to $19/mo for 10 GB
  • Upstash 10 K cmd/day is generous but hard-capped
  • Ops burden higher — you own the pipeline
C) PocketBase
  • Single-node — no horizontal scale until you rewrite
  • SQLite → concurrent writes throttled
  • No native background job runner
  • Community-scale project; support is Discord
D) Cloudflare
  • Workers 100 K req/day is easy to blow through
  • D1 lacks full SQL surface (no RLS yet)
  • Runtime is not Node — libraries must be edge-safe
  • Long-running jobs need Queues (paid ≥ 1 M msg/mo)

My recommendations by situation

If you want data-in-cloud this week
→ A) Supabase

Fastest path. Postgres schema from the doc drops in verbatim. RLS policies map 1:1 to what's already designed. You'll be logging in to app.supabase.com to eyeball rows within an evening.

If you're building a real product
→ B) Neon + Fly + FastAPI

Every line matches the architecture doc. No lock-in; move to AWS/GCP later without re-writing. Same code from pilot to Chain tier.

If you want the world's simplest hosted DB
→ C) PocketBase

One binary, one dashboard, one file. Perfect for 1–10 outlets forever. Migrating to B) when you outgrow it is a straight PG dump-and-restore.

If storefront traffic is your primary load
→ D) Cloudflare

Storefront read heavy? Edge everywhere makes it snap. Pair Workers with D1 for storefront + option B for the heavy admin side later.
